## 1. データ契約(入力仕様)

### 1-2. エンコーディング(重要な落とし穴)
- 両 CSV とも **UTF-8 + BOM(先頭 `EF BB BF`)**。読み込み時に BOM を除去する。
- 中身は正しい UTF-8。※ターミナルに出すと文字化けして見えることがあるが、**データは壊れていない**
  (Windows コンソールの表示エンコーディングの問題)。デコードは常に UTF-8 で行う。

### 1-3. `Order History.csv` の使用カラム(全28列中、使うのはこれだけ)
| カラム名(正確に) | 用途 | 例 |
|---|---|---|
| `Payment Method Type` | カード判定 | `Visa - 5171` / `Gift Certificate/Card and Visa - 5171` |
| `Order Date` | 日付フォールバック | `2026-06-29T14:30:46Z` |
| `Ship Date` | **計上日の基準(既定)** | `2026-06-30T03:50:57.832Z`(ミリ秒あり) |
| `Product Name` | 品目 | `サンナップ(Sunnap) 紙コップ ...` |
| `Total Amount` | 金額(税込・送料込・割引後) | `2,200`(カンマ区切り) |
| `Order ID` | 合算キー | `503-9219336-1401461` |
| `Order Status` | キャンセル除外 | `Closed` / まれに `Cancelled` |

### 1-4. `Refund Details.csv` の使用カラム
| カラム名 | 用途 | 例 |
|---|---|---|
| `Order ID` | 返金を注文に紐付け | `503-2593646-0152603` |
| `Refund Amount` | 返金額(注文から差引) | `200` |

### 1-5. 日付フォーマットの注意
- ISO8601・末尾 `Z`(UTC)。**ミリ秒を含む場合がある**(`...:57.832Z`)。JS の `new Date(iso)` で解釈可。
- **JST への変換が必須**(既定)。`toISOString()` は UTC を返すので使わない。次の手順で計算する:
  ```js
  // iso 例: "2026-07-08T21:06:11.011Z" → JST日付 "2026-07-09"
  const t = new Date(iso).getTime() + 9 * 3600 * 1000; // +9h
  const j = new Date(t);
  const ymd = `${j.getUTCFullYear()}-${String(j.getUTCMonth()+1).padStart(2,'0')}-${String(j.getUTCDate()).padStart(2,'0')}`;
  ```
  UTC モード時は `+9h` を足さずに同じ `getUTC*` で読む。

## 2. 変換アルゴリズム(確定・`amazon_to_zaim.py` と等価)

```
入力: orderRows[], refundRows[], 設定{ card, tz(jst|utc), aggregate, category, subcategory, store, source }

1. refundByOrder = {}                      // Order ID → 返金合計
   for r in refundRows: refundByOrder[r.OrderID] += parseAmount(r["Refund Amount"])

2. picked = []                             // 抽出対象の明細
   for row in orderRows:
       if card NOT in row["Payment Method Type"]: continue      // 部分一致(ギフト券併用も拾う)
       if row["Order Status"] in {Cancelled, Canceled}: continue // キャンセル除外
       if parseAmount(row["Total Amount"]) is invalid: continue
       picked.push(row)

3. (aggregate=false の旧挙動) 明細1行=1エントリ。日付=shipDate、返金無視。→ 通常は使わない

4. groups = {}                             // key = (OrderID, 計上日文字列)
   for row in picked:
       date = formatDate(row["Ship Date"] or row["Order Date"], tz)
       key  = OrderID + "\t" + date
       groups[key].amount += parseAmount(row["Total Amount"])
       groups[key].names.push(row["Product Name"])
       groups[key].date = date

5. 返金を差引:
   for orderId, refund in refundByOrder:
       該当 = groups の中で key の OrderID==orderId のもの
       if 該当なし or refund<=0: continue
       target = 該当のうち date が最も新しいグループ
       target.amount -= refund

6. 出力行:
   for g in groups:
       if g.amount <= 0: skip(全額返金など)      // 注記に残す
       row = [ g.date, category, subcategory, store, source, combineNames(g.names), String(g.amount) ]
   日付昇順にソート

補助:
  parseAmount(s)  = s から "," "¥" 空白を除去 → 整数(round)。不能なら invalid
  combineNames(names) = 出現順を保ちつつ同名を統合し "×N" を付す。区切りは " / "
                        例: ["今治","今治"] → "今治×2"、["A","B"] → "A / B"
```

### 出力 CSV 形式(ゴールデンと一致させる)
- ヘッダ(固定・順序厳守): `日付,カテゴリ,カテゴリの内訳,お店,支払い元,品目,支出金額`
- **カンマ/引用符/改行を含むフィールドは CSV クオートする**(品目にカンマが入り得る)。
  PapaParse `unparse` か同等のクオート実装を使う。
- **バイト一致させるなら**: 先頭に UTF-8 BOM、行末は **CRLF**(`\r\n`)。
  (ゴールデンは BOM+CRLF。行単位比較で検証するなら BOM/改行差は無視してよい)

### 固定値の既定
`category=生活費` / `subcategory=ゆうすけインポート` / `store=Amazon` / `source=ゆうEPOS`

## 8. 落とし穴チェックリスト(先人が踏んだ順)

- [ ] BOM を除去して読む(付いたまま `ASIN` が `﻿ASIN` にならないように)。
- [ ] 日付は **JST 変換してから** YYYY-MM-DD 化(`toISOString` は UTC で誤り)。ミリ秒付き ISO に対応。
- [ ] カード一致は**部分一致**(`includes`)。完全一致だとギフト券併用を取りこぼす。
- [ ] **カード下4桁1つで絞らない**。カード更新・再発行で番号が変わると、その時点以降が
      丸ごと落ちる(2026-07 に実際に発生・41,139円)。利用期間を見て複数指定する。§9-2
- [ ] `Ship Date` / `Shipment Status` は **`" and "` で連結される**ことがある(複数出荷)。
      連結値は日時としてパースできないので、先頭値を取り出してから TZ 変換する。§9-4
- [ ] `Total Amount` はカンマ除去してから数値化。
- [ ] 合算キーは (Order ID, **計上日**)。日付を跨ぐ分割発送は別エントリ(実データには無いが将来対応)。
- [ ] 返金は Order ID 単位。該当注文が抽出対象に無ければ無視。net≤0 は出力しない。
- [ ] 品目にカンマが入り得るので **CSV クオート**する。
- [ ] 実データ(ZIP・住所入り CSV・生成 CSV)は **git に含めない**。
- [ ] バイト一致を狙うなら BOM + CRLF。狙わないなら行単位比較で BOM/改行差を無視。

## 9. Zaim 実績との突合(2026-09-06)― 見つかった欠陥と対策

**背景**: 最新の `Your Orders (1).zip`(2026-09-02 までの235明細)と Zaim エクスポート
`Zaim.20260906010837.csv`(2026-02-01〜07-31)を1件ずつ突合した。**カード連携で Zaim に入っている
実績を「正」として、ロジックの出力に過不足が無いか**を検証したもの。

### 9-1. 突合結果(ゆうEPOS = Amazon 上は 5171 と 7474)

| | 件数 | 合計 |
|---|---|---|
| Zaim 実績(カード連携) | 29件 | 93,080円 |
| **修正前(カード5171のみ)** | **24件** | **76,668円** |
| 修正後(5171+7474・ギフト券補正あり) | 27件 | 95,649円 |

差額はすべて説明でき、端数なく一致した:

```
76,668 (修正前) + 20,650 (7474で欠落) − 1,669 (ギフト券過大) − 2,569 (Zaim側の漏れ) = 93,080
```

月次でも 6か月中 5か月が**1円まで一致**する(残り1件は下記 D)。

| 月 | Zaim 実績 | 修正後ロジック | 差 |
|---|---|---|---|
| 2026-02 | 3件 7,892円 | 3件 7,892円 | 一致 |
| 2026-03 | 0件 0円 | 1件 2,569円 | **+2,569円**(D: Zaim 側の漏れ) |
| 2026-04 | 7件 30,705円 | 7件 30,705円 | 一致 |
| 2026-05 | 7件 17,982円 | 7件 17,982円 | 一致 |
| 2026-06 | 6件 5,612円 | 4件 5,612円 | 一致(件数差は B) |
| 2026-07 | 6件 30,889円 | 5件 30,889円 | 一致(件数差は C) |

### 9-2. 欠陥 A(重大): カード再発行で下4桁が変わると以降が丸ごと落ちる

- Amazon 登録カードは **2026-07-09 の出荷を最後に `Visa - 5171` が消え、2026-07-19 から
  `Visa - 7474`** に変わっている(EPOS の更新)。Zaim 上はどちらも同じ「ゆうEPOS」。
- 下4桁1つで絞る旧実装では **7474 の 9件 / 41,139円(2026-07-19〜2026-09-03)が消えた**。
  月次出力にすると 2026-07 がちょうど切替月で、片方しか選べないと半分しか出ない。
- **対策**:
  - `convert(rows, refunds, {cards: ['5171','7474']})` で複数カードを合算(`card` 単体も後方互換)。
  - `detectCards()` がカードごとの利用期間(`firstDate`/`lastDate`)を返す。
  - `suggestSuccessors(cards, selected)` が「選択カードが使われなくなった後に始まったカード」を
    後継候補として返し、UI が警告＋ワンタップ追加を出す。
  - Python 版は `--card 5171,7474`。

### 9-3. 欠陥 B: ギフト券併用注文はカード実請求額と一致しない

- `2026-05-20 Matdeco 冷感敷きパッド`: 注文総額 **5,760円** / EPOS 実請求 **4,091円**(差 1,669円)。
- Order History にギフト券充当額の列は無い(`Total Discounts` は 0、
  `Shipment Item Subtotal 5,236 + Tax 524 = 5,760`)ため、**データからは復元できない**。
- **対策**: `amountOverrides: { '<OrderID>\t<計上日>': 実請求額 }` で手動補正できるようにし、
  UI のギフト券警告に実請求額の入力欄を置いた。補正は処理メモに残る。
- なお `warnings[].key` が上書き用キー、`warnings[].rawAmount` が補正前の金額。

### 9-4. 欠陥 C: 複数出荷の明細はカード側で分割計上される

- `2026-07-21 収納ボックス 9,900円` は Amazon では1明細だが、EPOS は **4,950円×2件**。
  要因は数量ではなく **出荷回数**(この注文は2回に分けて出荷された)。
  数量2でも1回の出荷なら分割されない(実データのセロテープ 564円で確認)。
- Amazon はこのとき `Ship Date` を `"2026-07-21T08:14:39.090Z and 2026-07-21T08:14:53.428Z"` と
  **`" and "` で連結**し、`Shipment Status` も `"Shipped and Shipped"` になる(旧エクスポートには0件・今回初出)。
- **金額の合計は一致するので勘定はズレない**が、Zaim と1対1で突合できないので注記を出す。
- **同時に潜在バグを修正**: 連結値は `Date.parse` / `fromisoformat` が失敗し、
  `raw[:10]` フォールバックで **TZ 変換が飛んでいた**。今回はたまたま正解だったが、
  UTC 15:00 以降の出荷なら1日ズレる。`splitDateValues()` で先頭値を取り出してから変換する。

### 9-5. D: Zaim 側の記録漏れ(ツールが埋めるべき差分)

- `2026-03-02 アオビホ PCスタンド 2,569円`(`Closed`/`Shipped`・返品なし)は Order History に
  存在するが、**Zaim には全期間どこにも無い**(金額全件検索で0ヒット)。カード連携の取りこぼし。
- これは欠陥ではなく、**本ツールで取り込むべき正当な差分**。

### 9-6. 計上日について(既知の許容差)

- 一致した23件のうち Zaim の日付と `+0日` が12件、`+1日` が11件。EPOS の利用日は
  注文日基準と出荷日基準が混在しており、**どの基準でも完全一致はしない**
  (UTC 出荷日にすると16件が一致し JST より良いが完全ではない)。
- 今回のデータでは **JST/UTC で月が変わる明細は0件** で、月次出力の勘定に影響しない。
  月末出荷では月ズレが起こり得るため、既定は JST 発送日のまま UI で切替可能に残す。

### 9-8. コードレビューで塞いだ「静かに壊れる」経路(2026-09-06)

補正機能そのものが別の操作で無言に破綻しないよう、次を修正した(いずれも回帰テストあり)。

| 症状 | 原因 | 対策 |
|---|---|---|
| 月次で切り出しているのに、他の月のギフト券注文が警告欄に並ぶ | `warnings` / `notes` に期間フィルタが効いていなかった | `warnings` は出力対象のグループだけに絞り、`notes` は計上日つきで貯めて同じ範囲で絞る |
| 実請求額を入力した後に「発送日/注文日」「JST/UTC」を切り替えると、補正が**無警告で外れて総額に戻る** | 上書きキーが計上日を含み、設定変更でキーがズレていた | 1注文=1グループなら **Order ID 単独のキー**も受け付ける(`warnings[].overrideKey`)。どこにも当たらない上書きは `unmatchedOverrides` と注記で必ず表に出す |
| 同じ ZIP を選び直すと、期間プルダウンは「7月」表示のまま出力は全期間になる(**Zaim で重複計上**) | 選択肢の再構築をスキップする際に、表示値と `state` の同期まで飛ばしていた | 再構築の有無にかかわらず、最後に必ず `select.value` と `state.period` を一致させる |

### 9-9. 画面の整理と日単位の期間指定(2026-09-06 後半)

**常時見せるのはカードと期間だけ**にした。計上日(発送日/注文日・JST/UTC)・まとめ方・固定値は
ユーザーが選ぶことのない設定なので `<details id="advanced-settings">` に畳んだ。**消してはいない**
(UTC 切替などは PLAN.md §11 で「UI に残す」と決めているため)。

期間は **開始日・終了日の2つの日付が真実の源**で、プルダウン(全期間 / 各月 / 日付で指定)は
その2値を埋めるショートカット。これで月次でも1日単位でも同じ仕組みで切り出せる。

- `convert()` の `dateFrom` / `dateTo` はもともと日付単位なので、コアの変更は
  `range`(期間フィルタ前の全体レンジ。日付入力の初期値に使う)を返すだけ。
- ファイル名: 全期間=`_all` / 月ぴったり=`_2026-07` / 1日=`_2026-07-21` / 範囲=`_2026-07-19_2026-07-21`。
- **落とし穴1**: WebKit(iOS Safari を含む)では `input[type=date]` の `change` が
  発火しないことがある(Playwright の WebKit で実際に再現)。`input` も購読し、
  値が空か完全な `YYYY-MM-DD` のときだけ反映する。
- **落とし穴2(重大)**: 日付欄は未指定のとき**データ全体の端を「表示上の初期値」として
  出しているだけ**で、`state` は空文字のまま。ここで「触っていない側の表示値」まで
  確定させると、**後からカードを足したときにその日付より前の明細が無警告で落ちる**。
  (7474 だけ選んで終了日を直す → 開始日が 7474 の初回利用日 2026-07-19 で固定 →
  あとから 5171 を足しても、5171 の 2026-07-19 より前が出てこない。まさに本件で
  直したはずの「取りこぼし」が別経路で再発する。)
  → `onDateInputChange(source)` は**編集された側だけ**を `state` に反映する。
  例外は「開始 > 終了」になる入力のみで、その結果は日付欄にそのまま表示される。
- 「日付で指定」を選んだ状態は `state.customPeriod` で保持する。保持しないと、
  範囲がたまたま全期間と同じ場合に選択が即座に「全期間」へ巻き戻り、操作が
  何も起きていないように見える。
- 選択中の期間がカードのデータと**1日も重ならなくなったら**(カード切替時に起こる)、
  全期間へ戻してメッセージを出す。0件のまま日付ピッカーが範囲外を指し続けると
  「このカードには何も無い」と誤読される。ただし**自分で打った日付が範囲外の場合は戻さない**
  (意図した指定を勝手に消さない)。
- **落とし穴3**: `<input type=date>` は年や日のセグメントを1つ消しただけでも
  `value` が `""` になる。これを「クリアした」と解釈して再描画すると、
  **打ち直している最中の欄がデータ先頭日へ飛ばされ、件数も全期間へ戻る**。
  空値は `change` / `blur`(確定)でのみ反映し、打鍵途中(`input`)では無視する。
  あわせて、日付欄の編集に起因する再描画では**その欄への書き戻しをしない**
  (`dateEdit` で判定。フォーカス追跡は blur の発火順に依存して取り残しが出る)。
- **落とし穴4**: ネイティブの日付入力は min-content 幅が広く、`display:grid` の
  既定 `auto` トラックだと**カラムごと膨らんで 320px 幅で横スクロールが出る**
  (Chromium で 16px。WebKit では出ないのでエンジンを跨いで見ないと気付けない)。
  `main { grid-template-columns: minmax(0, 1fr) }` + `.card { min-width: 0 }` で止める。
  なお溢れの判定に `window.innerWidth` を使うと、モバイルエミュレーション時に
  実幅より大きくなって**溢れを隠す**。`document.documentElement.clientWidth` と比べること。
