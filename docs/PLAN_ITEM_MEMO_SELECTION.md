## 2. A: メモを 100 文字に収める

### 決めたこと

- `web/js/core.js` の `buildMemo()` / `scripts/amazon_to_zaim.py` の `build_memo()` を書き換える。
- 定数を 1 か所に置く。
  - `FIELD_MAX_LEN = 100` … Zaim の 1 項目に入る最大文字数(実機で確認済み)
  - `MEMO_MODES = ['notes', 'none', 'full']`
- メモの中身を 3 モードにする。**既定は `notes`**。

| モード | 中身 | 想定文字数 |
|---|---|---|
| `notes`(既定) | 返金 / ギフト券 / 複数出荷の注記 + `注文 <Order ID>` | 20〜80 |
| `none` | 空欄 | 0 |
| `full` | 全商品名 + 注記 + 注文ID(従来の中身。100 文字で切る) | ≤100 |

### 既定を `none`(空欄)ではなく `notes` にする理由

ユーザーからは「そもそもメモは空欄でも良いかも」という提案だが、メモに載っている注記は
**あとからカード明細と突合するときに要る情報**で、消すと差異の原因が追えなくなる:

- 「返金○円を差引済み」… Amazon の注文額とカード請求額が違う理由
- 「ギフト券併用のため実請求額と差がある可能性あり」… 過大計上の可能性がある行の目印
- 「N回に分けて出荷」… カード明細では複数件に割れている行の目印
- `注文 503-…` … Amazon 側の注文ページを引くキー。二重取込の判定にも使う

商品名は**品目欄が持つようになる(§3)**ので、メモから外しても「何を買ったか分からない」にはならない。
空欄にしたい人は詳細設定で `none` を選べる。

### 実装上の注意

- `full` のとき、**注記を先に確保してから残り枠に商品名を入れる**。商品名を先に詰めると、
  返金・ギフト券の注記が末尾から押し出されて静かに消え、金額のズレに気付けなくなる。
- 切り詰めは**コードポイント単位**で行う(`Array.from()` / Python の `str`)。
  JS の `slice()` はサロゲートペアを分断し、UTF-8 書き出し時に `�` になる(既存 `shortenName` と同じ轍)。
- 共通の `truncate(text, maxLen)` を core / py 両方に置き、品目(§3)と共用する。

### 受入基準

1. すべての出力行で `文字数(メモ) <= 100`。**単体テストで全行を検査する**(1 件抜き取りでは意味がない)。
2. 実機の再現ケース(乳液 + 浄水器カートリッジ)で、メモが `注文 503-…` だけになる。
3. `full` モードで、返金 + ギフト券 + 複数出荷が同時に立つ注文でも**注記が 3 つとも残る**。
4. Python 参照実装と JS の出力が**バイト単位で一致**(`node scripts/verify_dummy.js`)。

## 3. B: 品目に「買ったもの」を並べる

### 決めたこと

`itemLabel()` / `item_label()` を「先頭 + ほかN点」から、**予算いっぱいまで商品名を並べる**方式へ変える。

```
現在: なめらか本舗 モイスチャライジング 乳液 NC… ほか1点
変更: なめらか本舗 モイスチャライジング 乳液 NC… / ブリタ マクストラプロ ピュアパフォーマンス 浄…
```

- 1 商品あたりの見出し長 `ITEM_MAX_LEN = 24` と `shortenName()`(`【まとめ買い】` などの宣伝ブロック除去)は**そのまま維持**。
- 同名は従来どおり `×N`。
- 区切りは既存の `ITEM_JOIN = ' / '`。
- 予算(品目欄全体の上限)を超えそうなら、**そこから先だけ**「ほかN点」に畳む。

### アルゴリズム(擬似コード・両言語で同一にすること)

```
labels = 商品種類ごとに [shortenName(名前) + (個数>1 ? "×個数" : "")]
text = labels[0]; shown = 1
for i in 1..labels.length-1:
    candidate = text + " / " + labels[i]
    rest      = labels.length - i - 1          # これを入れたとき残る点数
    tail      = rest > 0 ? " ほか{rest}点" : ""
    if 文字数(candidate + tail) > 予算: break   # ここから先は畳む
    text = candidate; shown = i + 1
omitted = labels.length - shown
return truncate(omitted > 0 ? text + " ほか{omitted}点" : text, 予算)
```

`tail` を先に足して判定するのが要点。これを忘れると「ほかN点」を付けた瞬間に予算を超える。

### 未確認事項(実装前に確認したい)

**Zaim の「品目」欄の文字数上限は未確認**。実機で赤字が出たのはメモ(100文字)だけで、品目は分からない。

- 暫定案: 品目も `FIELD_MAX_LEN = 100` を予算にする。
- 確認方法: Zaim アプリの品目欄に 100 文字強を貼って保存できるか見る。上限が小さければ定数を分ける
  (`ITEM_FIELD_MAX`)。**定数を 1 か所に置いておけば、判明後の修正は 1 行で済む**ようにしておくこと。
- 家計簿の一覧で読める長さという観点では、実用上は 60 文字程度でも足りる。**迷ったら小さい方(安全側)**。

### 受入基準

1. 2 品の注文で両方の名前が出る(「ほか1点」が消える)。
2. 商品種類が多い注文で `A… / B… / C… ほか3点` の形になり、全体が予算内。
3. 1 種類だけの注文の出力は**従来と変わらない**(`サンプル柔軟剤 …` / `… ×2`)。

## 4. C: 「1 つの支払いの中で複数明細」について

### 4-1. 結論: Zaim の CSV 取込では実現できない

`docs/IMPLEMENTATION.md` §10 に記録した、Zaim「ファイル入出力 → 一般的な CSV ファイルをアップロードする」の
設定項目は次のとおりで、**1 行 = 1 記録**として取り込まれる:

```
日付 / カテゴリ / カテゴリ内訳 / メモ / お店 / 支払元 / 入金先 / 品目 / 支出の金額 /
収入の金額 / 振替の金額 / 振替か判別する列 / 集計の設定 / 金額表示 / タイトル / 区切り文字
```

- **複数行を 1 記録にまとめる列(取引ID・グループキー等)が無い**。
- **品目の列は 1 つだけ**。実機の「品目を追加」に相当する構造を CSV から作る手段がない。

したがって「1 レコードに複数品目」は**取込 CSV の仕様上不可能**。手入力か API 以外に道はない。

> **TODO(将来)**: Zaim の公式 Web API(`/v2/home/money`)なら 1 取引に複数品目をぶら下げられるか未調査。
> できるならブラウザから直接登録する経路(CSV を介さない)が最終形になりうる。
> ただし OAuth と API キー管理が要り、「端末内で完結・外部送信なし」という本ツールの前提が変わる。
> **今回のスコープ外**。やるなら別 PLAN を切る。

### 4-2. 代替: 「商品ごとに 1 行」モード(`splitByItem`)

同じ支払いでも**商品ごとに行を分ける**モードを足す。Zaim 上は別レコードになるが、
1 件ずつ品目が残るので「何を買ったか」は完全に残せる。合計金額は合算モードと一致する。

- 実装: グループ化キーに商品名を足すだけ。
  `key = splitByItem ? "<注文ID>\t<計上日>\t<商品名>" : "<注文ID>\t<計上日>"`
  (合算モードのキー形式は**変えない**。`amountOverrides` のキーが `"<注文ID>\t<計上日>"` 前提のため)
- 金額は各明細行の `Total Amount`(Amazon の Order History は**明細 1 行 = 1 商品**で金額を持っている。確認済み)。
- UI では既定にしない。**カード明細との 1:1 突合が崩れる**ことを画面に明記する
  (「カード明細の 1 件が複数行になります。合計は変わりません」)。

#### 返金の按分ルール(ここだけ既存挙動が変わる)

現在は「注文内で**最も遅い発送日**のグループから返金を全額差し引く」。商品ごとに分けると、
1 商品の金額を超える返金がそのグループだけにぶつかり、**その行が実質マイナスで丸ごと落ちて、
同じ注文の他の行が返金前の金額のまま残る**(= 過大計上)。

方針: **注文内で「発送日が新しい順 → 金額が大きい順」に、0 円になるまで順に充当する**。
使い切れなかった返金は握り潰さず、注記に出す(例: `返金 3,000円のうち 800円は差し引く明細がありません(注文 …)`)。

- 合算モード(既定)でも、複数出荷の注文では挙動が変わりうる。
- **必ず `node scripts/verify_equivalence.js` を手元の実データで流し、39 件 / 126,896 円が動かないことを確認する**。
  動いた場合は差分の注文を 1 件ずつ見て、新しい方が正しいことを確認してから golden を更新する。

### 受入基準

1. `splitByItem` ON で、2 品の注文が 2 行になり、**合計金額が合算モードと一致**する。
2. Python 参照実装(`--split-items`)と JS 出力が一致する。
3. 既定(OFF)の出力は**この変更前とバイト単位で同じ**(返金按分の影響を除く)。

## 5. D: カテゴリの内訳を 2 択にする

### 決めたこと

- 選択肢は `ゆうすけAmazon` / `ともかAmazon` の **2 つだけ**。その他は出さない(将来増えたら改修する)。
- 置き場所: **STEP 2 の「出力する期間」の直下**(日付入力のすぐ下)。毎回選ぶ項目なので詳細設定に畳まない。
- UI は既存の `.radio-chip`(計上日・まとめ方と同じ見た目)を流用。`name="subcategory"`。
- **詳細設定の「カテゴリの内訳」自由入力(`#opt-subcategory`)は削除する。**
  自由入力だと打ち間違いがそのまま新しい内訳として Zaim 側に増える。
- 定数 `SUBCATEGORY_CHOICES = ['ゆうすけAmazon', 'ともかAmazon']` を core に置き、UI はそこから作る。
- 既定値を変更: `DEFAULT_OPTIONS.subcategory` / `DEFAULT_SUBCATEGORY` = `'ゆうすけAmazon'`。
- カテゴリ(`生活費`)・お店(`Amazon`)・支払元(`ゆうEPOS`)は**現状どおり詳細設定の自由入力のまま**でよい。

### 提案(採否は実装側で判断)

出力ファイル名に内訳を入れると、二重取込の管理がしやすい:
`zaim_import_5171-7474_2026-07_ゆうすけ.csv`。日本語ファイル名を嫌うなら `yusuke` / `tomoka`。

### 影響

- ダミーの golden CSV 2 本の 3 列目が変わる → **再生成が必要**(§8)。
- `web/js/core.test.js` の期待値(`'ゆうすけインポート'` を直書きしている箇所が数か所)。

## 6. E: 出力する行をチェックボックスで選ぶ

### 決めたこと

プレビュー表(`#preview-table`)の**左端にチェックボックス列**を足し、**チェックが付いている行だけを CSV に出す**。

- ヘッダ行のチェックボックスは全選択 / 全解除。一部だけ選択中は `indeterminate` にする。
- 既定は**全チェック**(今の挙動と同じ CSV が出る)。
- 選択状態は `state.excluded = Set<key>`(= 外した行を覚える)で持つ。
  「選んだ行を覚える」ではなく「外した行を覚える」にするのは、期間やカードを変えて**行が増えたとき、
  新しい行が既定で出力対象**になるようにするため。
- キーは `convert()` が返す `meta[i].key`(= `"<注文ID>\t<計上日>"`、分割モードでは商品名込み)。
  - **要修正**: 現状 `aggregate: false` の分岐だけ `meta.key` が空文字 `''` になっている。
    ここに一意なキー(`"<計上日>\t#<連番>"` 等)を入れないと、非合算モードで全行が同一キーになり、
    1 行外すと全行が消える。
- チェックを外した状態は、カード・期間・詳細設定を変えても**キーが一致する限り維持**する。
  ZIP を読み直したときは**リセット**する(別のデータなので引き継ぐと危険)。

### 画面への反映

| 要素 | 変更 |
|---|---|
| 件数チップ `#sum-count` | 選択中の件数。**全選択時は従来どおり `N件`**、一部選択時のみ `N件(全M件中)` |
| 合計チップ `#sum-total` | 選択中の合計金額 |
| ダウンロード / 共有 / コピー | 選択 0 件のとき無効化し、`#empty-result` に「出力する行が選択されていません」と出す |
| ファイル名 | 変更不要(期間タグは今のまま) |
| 表の下の hint | 「チェックを外した行は CSV に含まれません」を追記 |

`#sum-count` の文字列は E2E が `=== '5件'` で見ているので、**全選択時のフォーマットは絶対に変えない**。

### レイアウト上の注意

- チェックボックス列は幅を固定(`width: 2.2rem` 程度)し、**320px 幅で横スクロールが出ないこと**。
  E2E に「横オーバーフローなし」の検査があるので、日付列・金額列の幅配分を見直す必要があるかもしれない。
- タップ target は 44px 四方を確保(iPhone 実機で押しにくいと使われない)。`<label>` でセル全体を当たり判定にする。

### 受入基準

1. 1 行外すと、CSV の行数が 1 減り、合計がその金額分減る。
2. カードを追加 → 増えた行は**チェック済み**で出てくる。外した行は外れたまま。
3. 全解除 → ダウンロードが無効になり、案内が出る。
4. 320px 幅で横スクロールが出ない。

## 8. F: 明細データが GitHub に無い件(検証をどう回すか)

実データ(`data/`)は PII を含むため `.gitignore` 済みで、**GitHub には上がっていない**。
そのため CI で回せるのは `testdata/dummy` だけ。検証は 3 段構えにする。

1. **ダミー(CI で回る)**: `node --test web/js/core.test.js` / `node scripts/verify_dummy.js`
   - golden 再生成手順:
     ```bash
     python scripts/amazon_to_zaim.py --base testdata/dummy --card 5171
     python scripts/amazon_to_zaim.py --base testdata/dummy --card 7474
     ```
     → `testdata/dummy/output/zaim_import_{5171,7474}.csv` が更新される。**必ず差分を目視**してからコミットする。
2. **実データ(手元でのみ)**: `node scripts/verify_equivalence.js`
   - **39 件 / 126,896 円が変わっていないこと**が今回の最重要チェック(§4-2)。
3. **実機 Zaim**: 出力 CSV を「アップロードをテスト」で 1 回通し、**メモが赤字にならないこと**と
   品目の見え方を確認する。ここまでやって初めて完了。

| 1 | **全出力行**のメモが 100 文字以下 | 1 件抜き取りでは長い注文を取りこぼす。今回の不具合そのもの |
| 2 | 全出力行の品目が予算以下 | 同上(品目の上限が判明したら値を差し替え) |
| 3 | `full` モードで注記 3 種が同時に残る | 商品名を先に詰める実装だと注記が静かに消える |
| 4 | 2 品の注文で両方の商品名が品目に出る | 「ほか1点」の退行検知 |
| 5 | `splitByItem` の合計が合算モードと一致 | 分割で金額が increase/decrease したら即バグ |
| 6 | 1 商品の額を超える返金が注文内で按分される | §4-2。過大計上に直結する |
| 7 | 行を外すと CSV の行数・合計が連動する(E2E) | 選択機能の芯 |
| 8 | カード追加で増えた行は既定でチェック済み(E2E) | `excluded` を「外した行を覚える」にした理由の担保 |
| 9 | 内訳ラジオの切替が CSV の 3 列目に出る(E2E) | 取込先の内訳を間違えると家計簿が汚れる |

## 10. 実装順序(推奨)

1. **core.js の A・B**(メモ・品目)+ Python 同期 → 単体テスト更新 → ダミー golden 再生成 → `verify_dummy`
2. **実データで `verify_equivalence`**(金額が動いていないことをここで確定させる)
3. **D**(内訳 2 択)→ golden 再生成 → テスト更新
4. **C**(`splitByItem`)+ 返金按分 → 両言語の一致確認 → 実データ再チェック
5. **E**(チェックボックス)→ E2E 追加 → 320px レイアウト確認
6. ドキュメント(README / IMPLEMENTATION §10-3・§4-1 の制約)
7. 実機 Zaim で 1 件テスト取込

1〜2 を先にやるのは、**金額に影響しない変更であることを早い段階で確定させる**ため。
ここが崩れたまま先に進むと、後段の変更と原因が混ざって切り分けができなくなる。

## 11. 決着済みの判断(実装時に蒸し返さないこと)

- メモの既定は `notes`(空欄ではない)。理由は §2。
- 品目は「宣伝ブロック除去 + 24 文字 / 商品」を維持したまま**並べる**。1 商品を長く出す方向には振らない。
- 「1 支払い = 複数明細」は CSV 取込では**できない**。代替は行分割。API は今回のスコープ外(§4-1)。
- カテゴリ内訳は**選択肢に閉じる**(自由入力は廃止)。増やすときはコードを直す。
- 出力選択は「**外した行を覚える**」方式。「選んだ行を覚える」にしない。
